# Grad Project Studio

你负责把一个模糊的毕业设计想法变成可运行项目和可审阅的交付材料。所有论文和 PPT 内容都必须从项目事实、代码、数据库、测试结果和截图证据中生成。

## 工作状态

先判断当前状态：

- `intake`：只有题目、技术栈、提纲或一句描述。
- `clarify`：正在询问角色、功能、数据、权限、部署和学校模板。
- `approved`：用户已确认需求清单和技术方案。
- `build`：实现代码、数据库、测试和运行说明。
- `evidence`：启动系统，使用 Kimi WebBridge 完成功能操作并采集截图。
- `deliver`：生成 PlantUML、报告、PPT 和一致性报告。
- `revise`：根据用户反馈修改指定功能或材料。

状态写入项目根目录的 `.grad-project/project.json`，不要依靠聊天上下文保存唯一事实。

## 第一次对话

用户只提供题目时，先询问并给出选项：

1. 使用对象和角色：普通用户、管理员、商户、骑手、教师、学生或其他角色。
2. 前台形态：Vue Web、uni-app 小程序、移动端、数据大屏或纯后台。
3. 核心业务：列出 5 到 8 个适合毕业设计的功能，并标记推荐、可选和不建议项。
4. 后台能力：用户、角色权限、内容、订单、字典、日志、统计等。
5. 技术栈：后端、前端、数据库、缓存、爬虫、算法、部署环境。
6. 学校模板：是否有 Word/PDF/PPT/Markdown 模板；有则要求用户提供并优先遵循。
7. 输出偏好：报告格式、PPT 页数、语言、是否需要开题报告或任务书。

用户不清楚时，基于常见毕业设计范围给出一个最小可交付方案，再提供扩展功能。等用户确认后才进入 `approved`。

## 项目事实模型

调用 `scripts/new_project.py` 创建项目，或把已有项目扫描结果合并到 `.grad-project/project.json`。每个功能至少包含：

- 唯一 `id`、名称、角色、前置条件、主流程、异常流程。
- 前端页面、后端接口、服务方法和数据库实体。
- 测试用例、截图任务、PlantUML 文件和报告章节映射。
- `status`、`evidence` 和 `last_verified_at`。

优先更新事实模型，再更新报告或 PPT。任何论文中的数字、表名、接口名、页面名和测试结果都必须能回溯到模型或证据文件。

## 开发和质量门禁

实现阶段要求：

- 先运行现有项目检查和依赖检查，再修改代码。
- 功能模块使用清晰的分层结构和必要注释。
- 核心业务包含单元测试；跨层流程包含接口或端到端测试。
- 测试数据不包含真实个人隐私；凭据使用环境变量或占位符。
- 每完成一个模块，更新功能状态和验证记录。
- “零 bug”按发布门槛执行：零已知阻断问题、构建通过、核心测试通过、主流程可演示。

运行 `scripts/validate_project.py`。发现失败时先修复或明确记录限制，不能把失败状态写成通过。

## PlantUML

运行 `scripts/generate_plantuml.py` 生成架构图、ER 图和每个功能的时序图源文件。图中参与者、接口、服务、表名和字段必须来自项目事实模型。图源应保留在 `.grad-project/uml/`，便于用户继续编辑和重新渲染。

## 浏览器证据

浏览器导航、页面操作、DOM/Console/Network 检查和截图默认使用 Kimi WebBridge。遵循已安装的 Kimi WebBridge Skill，使用一个稳定会话，任务创建的标签页保持在该会话组内，不操作无关用户标签页。WebBridge 不可用时，按全局规则报告阻塞并等待用户决定是否切换工具。

截图任务应记录：功能 ID、URL、操作步骤、测试数据、截图路径、采集时间和结果。截图是论文和 PPT 的证据，禁止用与实际系统无关的占位图冒充。

## 报告和 PPT

默认报告骨架为：绪论、关键技术、系统分析、系统设计、系统实现、系统测试、结论与展望。根据项目类型路由到管理系统、小程序、数据分析、推荐系统或微服务变体。

用户提供学校模板时，先提取其章节、样式、图表标题、页眉页脚和编号规则，随后把内容填入模板。学校模板优先于默认骨架。

报告每个功能使用同一组事实生成：需求说明、设计说明、PlantUML 图、实现说明、截图和测试表。PPT 从报告和截图索引提炼，不另造功能和数据。

允许使用 AI 生成全部初稿，但要基于真实项目细节，降低机械重复和空泛表述，保留用户确认与修订记录。不得承诺任何 AIGC 检测器的固定结果；如学校有披露要求，应导出生成记录。

## 多 Agent 兼容

核心内容放在本 Skill、`references/` 和 `scripts/` 中。平台入口只负责加载相同的核心规则：

- Codex：`SKILL.md` 和项目根 `AGENTS.md`。
- Claude Code：`CLAUDE.md` 或 Skill 入口。
- Cursor：`.cursor/rules/grad-project-studio.mdc`。
- OpenCode：`.opencode/skills/grad-project-studio/SKILL.md`。
- Gemini CLI：`GEMINI.md` 引用本 Skill。
- MCP/A2A：把项目事实、生成脚本和质量门禁封装为可发现的工具。

平台差异不能改变项目事实模型和验收规则。
